## MED findings

### MED-1: the ratchet compares a subset run with the full baseline

- **Where.**
  - `tools/eval/gate.py:64-79`: `check_context` compares only profile, samples, adapter, scorer and fingerprint.
  - `tools/eval/gate.py:105-108`: the regression is computed on the *current* denominator,
    `expected = bf * c.den`, with no check that jobs or denominators equal the baseline's.
  - `tools/eval/run.py:137-143`: the shard is kept outside `run["samples"]`.
  - `tools/eval/run.py:461-463`: the shard is never recorded in the run section.
  - `tools/eval/run.py:689-693`: ratchet is allowed together with `--shard`.
  - `tools/eval/run.py:723-731`: `aggregate --gate ratchet|targets` accepts any subset of shard files.
- **Failure.**
  - `python -m tools.eval.run --profile ci --shard 1/2 --gate ratchet` gates on half the jobs.
  - So does aggregating with one shard file missing.
  - The docstring claim at `run.py:10-11` ("a partial run is never compared with the full baseline") holds only
    when no `--gate` is passed.
  - The T16 fix (`f728afb`) catches missing *renderings*, not missing jobs.
- **Reproduction** (my script; synthetic jobs scored by the real `metrics.job_record` and `gate.evaluate`). Shard 2
  regresses: it reads previous-column K values, so 10 criticals are missed silently.

  ```
  full run         jobs 20  M1 10/60  M2 0/10 -> ratchet passed=False exit=1
  --shard 1/2 run  jobs 10  M1 0/30   M2 0/0  -> ratchet passed=True  exit=0
  ```

  `run.resolve()` gives an identical compared context (`profile`, `samples`) for `--profile ci` and
  `--profile ci --shard 1/2 --gate ratchet`.
- **Fix.**
  1. Record `shard` in `run` and refuse ratchet/targets when it is set (exit 2).
  2. In `ratchet_failures`, require `cur.jobs == base.jobs` and equal M1, M2, M4 and M5 denominators per cell
     (they come from the GT and are fixed for a given fingerprint and samples), otherwise `GateConfigError`.
  3. Before ratchet/targets in `aggregate_main`, require complete cells: carry the planned job count per cell in
     each shard doc.
  4. Add HA-05 cases for `--shard` and for a partial aggregate.

### MED-2: changing a metric definition is invisible to the ratchet

- **Where.**
  - `tools/eval/generate.py:38-44`: the split fingerprint covers the GT-side modules only.
  - `match.py`, `metrics.py`, `review_sim.py`, `targets.py`, `gate.py`, `adapters/pipeline_v0.py` (including the
    v0 needs_review rules) and `ocr_cache.py` are not covered.
  - The adapter and scorer identity is a hand-maintained string, `"1"` (`pipeline_v0.py:43-46`).
  - `check_context` (`gate.py:64-79`) has nothing else to compare.
- **Failure.**
  - Loosening a comparator, eligibility cost or NR0 rule, or the M1/M2 counting, without bumping a version string
    lowers M1 and raises M2.
  - The ratchet treats that as an improvement and passes, with no "re-baseline + DECISIONS" stop.
  - PRD §11.4 says never weaken a metric definition to pass a gate. The only protection today is that a unit test
    happens to cover the changed line.
- **Reproduction.**
  - I monkeypatched `metrics._flagged` to count every row as needs_review, which is a definition change.
  - Result: M1 10/60 → 0/60 and M2 0/10 → 10/10, and `gate.evaluate("ratchet", …)` → passed=True.
  - `[m for m in judge_and_adapter_modules if m in generate._COMMON_MODULES]` → `[]`.
- **Fix.**
  1. Add a `judge_digest` to `metrics.json` `run`: SHA-256 over the sources of `match`, `metrics`, `review_sim`,
     `targets`, `gate`, `report`, `hygiene`, `adapters/*` and `ocr_cache`.
  2. Make `check_context` refuse a mismatch with exit 2 and a "re-baseline and log a DECISIONS line" message.
  3. Add an HA-05 test.

### MED-3: a heldout run can be narrowed to a single report

- **Where.**
  - `tools/eval/hygiene.py:43-46`: `check_cli` rejects only `--dump-failures`.
  - `tools/eval/hygiene.py:61-89`: `redact_heldout` has no minimum job count.
  - `tools/eval/run.py:117-143`: `--sample`/`--sample-n` mean "first N reports by id" and are accepted for
    heldout, as is `--shard`.
  - `tools/eval/run.py:520-532`: a heldout shard file holds that subset's redacted cell.
- **Failure.**
  - `--profile heldout --sample-n 1` yields M1–M7 for H001 alone.
  - Differencing `--sample-n k` against `k+1` gives every heldout report's own counts.
  - `--shard k/80 --shard-out f.json` writes a single job's cell to disk, an artifact in CI.
  - FR-5.4 says "Only aggregate metrics may be read" and plan §6.11 says "no per-job breakdown for heldout"; both
    are bypassed with supported flags.
- **Reproduction.**
  - All three argument sets above pass `run.resolve` + `hygiene.check_cli`.
  - A synthetic one-job cell labelled heldout redacts to `jobs = 1`, `M1 (1,1)`, `M2 (0,1)`, …: one report's
    outcome.
- **Fix.**
  1. In `check_cli`, refuse `--sample`, `--sample-n`, `--shard` and fractions below 1 whenever heldout is selected
     (exit 3).
  2. In `redact_heldout`/`shard_doc`, require the heldout cell's job count to equal the full cell size from the
     manifest (or at least a k-anonymity floor).
  3. CI already shards by whole split × rendering cells, so it is unaffected.
  4. Extend HA-06.

  - The `dka` and `respiratory_acidosis` clusters name pH, pCO2 and pO2 (`scenarios.py:398, 409`).

  - `blood_ph`, `pco2`, `po2`, `ionized_calcium` and `hs_troponin_t` each occur in **0 rows**.

  - pCO2 82 mmHg goes through the real pipeline as HIGH and is not flagged: a silent missed critical.

  - M5 also hides it whenever another critical sets the headline.

### MED-5: the gated M2 ignores whether a confirmed critical ends up CRITICAL (S3)

- **Where.**
  - `tools/eval/metrics.py:278-289`: M2 credits a matched row that is CRITICAL *or* needs_review before review.
  - M2-post (CRITICAL after review and scoring) is only a diagnostic (`metrics.py:412`) and is not in
    `targets.RATCHETED` (`targets.py:44`).
- **Failure.**
  - S3 is about the final state ("can never *end up* both not CRITICAL and not needs_review").
  - In v2, alerts come only from scoring the confirmed rows (FR-1.4).
  - A row flagged for any reason counts as recalled even if the confirmed value is then scored non-critical. An
    engine that marks HCO3 8 "critical-looking" but has no HCO3 limit passes M2 at 100% and never raises the
    critical banner.
- **Evidence.**
  - Gated M2 vs M2-post: dev native 77/100 vs 73/100, dev scan 66 vs 61, dev photo 50 vs 45 (dev numbers from the
    full run at `07e3bcd`), and test native 27 vs 26 (HEAD).
  - Scoring perfectly confirmed GT rows with `EngineFloorScorerV0` leaves **17/152** dev+test GT criticals not
    CRITICAL: 13 HCO3, 3 Hb > 21 and 1 WBC 75.6.
  - So after a perfect review, about 11% of criticals still raise no alert.
- **Fix.**
  1. Gate on M2-post as well: ratchet it now; in targets mode require M2 = M2-post = 100%.
  2. Or define recall as "CRITICAL or needs_review before review, AND CRITICAL after confirmation".
  3. Record it in DECISIONS before P2 cuts its baseline. Add an ME test: a flagged critical whose confirmed value
     the scorer leaves HIGH does not count.

### MED-6: the committed eval outputs are a partial run; the phase-end full run is absent at HEAD

  - `eval/report.md:7` reads "Profile: `ci`; splits: test"; `eval/metrics.json` has `run.splits == ["test"]`.
  - Commit `78f8025` overwrote the full-profile report and metrics from `07e3bcd` with CI-profile output.
  - `run.py:615`: `--out` defaults to `eval/`, so every `make eval` overwrites the phase-end record.
- **Failure.**
  - Plan §9 says to commit report.md and metrics.json only from a phase-end `make eval-full` and never to commit a
    partial `make eval` output over them.
  - At HEAD there is no dev section and no heldout aggregate (G2 unmet; FR-5.6 store; the Appendix E held-out
    evidence).
  - PROGRESS says the post-fix full run was "running". It is reported finished but is not committed.
- **Fix.**
  1. Commit the finished post-F1/F2 full-profile outputs.
  2. Write CI-profile runs to a separate path (for example `eval/ci/`), or have `_finish` refuse to overwrite a
     full-profile `eval/metrics.json` from another profile.
  3. Add a test that `make eval` cannot clobber the phase-end report.
  4. Once committed, this finding closes.
